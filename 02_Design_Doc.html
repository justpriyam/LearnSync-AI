SHEET 02

Data flow pipeline

Every feature — course, sprint, or interview — runs through the same three stages before anything reaches the user.

STAGE 1

Upload

PDF, text, PYQs, resume, or JD lands on the FastAPI upload endpoint and is validated for type and size.

STAGE 2

Embed & chunk

Text is split into coherent chunks and embedded into the Vector Database, scoped to that user's document.

STAGE 3

Generate

Only the retrieved chunks — never the open web — are handed to the LLM to produce quizzes, modules, or questions.

SHEET 03

Feature-level design

Same pipeline, three different jobs. Switch sheets to compare how each engine uses it.

The Automated Classroom

The LLM receives the full chunked outline of a document and proposes a hierarchical module structure — each module tagged with the exact source chunks it came from.

  • Every quiz question carries a source-chunk reference, checkable against the original document.
  • Cheat sheets are condensed summaries generated from the same chunk set as the module they belong to.
  • Progress is visible to the user while generation runs — no silent multi-second stalls.
inputchunked document outline
outputcourse → module → sub-topic
groundingchunk_id per module
renders inclassroom view (T.2)

The "Last-Minute" Exam Scheduler

A second document — Previous Year Questions — is mapped back onto the master syllabus via embedding similarity, then scored by how often each topic recurs.

  • Topics are ranked by PYQ frequency; low-yield filler is visually collapsed, not deleted.
  • The plan recomputes if a new PYQ set or deadline arrives — it's a re-runnable scoring function, not a one-off script.
  • Output is a day-by-day dashboard sized to the days remaining before the exam.
inputsyllabus + PYQ doc + deadline
scoringtopic frequency in PYQs
outputN-day sprint dashboard
renders inSprint Dashboard (T.2)

The Adaptive "Interview Sense" AI

Resume and job description generate an opening question. Each spoken answer is scored, and that score decides whether the next question gets harder or drops to a foundational check.

  • Web Speech API handles speech-to-text in, text-to-speech out — no third-party audio service.
  • The Interviewer State manager (T.3) is backend-authoritative; the browser only renders its decisions.
  • Every turn's score rolls up into a single end-of-session analytics report.

SHEET 06

Grounding, safety & open items

No feature is allowed to reach beyond the user's own uploaded documents. These are the questions still open before Phase 3.

01

Vector DB choice: ChromaDB for the Phase 0/1 sandbox — simplest to stand up locally. Revisit Pinecone once concurrent-user load is real.

02

Interviewer State should be backend-authoritative so difficulty logic can't be tampered with client-side; the browser only renders its output.

03

PYQ-to-syllabus topic matching needs an accuracy check before the Sprint ranking can be trusted for real exam prep.

04

Session and document storage limits, plus a deletion path for resumes and transcripts, need to be settled before onboarding real users.
